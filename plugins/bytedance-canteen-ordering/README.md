# 字节餐厅订餐

一个可直接在 Codex 中使用的 Aplus 订餐插件，核心 Skill 是 `order-bytedance-canteen`。它会为每位用户建立独立偏好，一次规划完所有午晚餐，连续完成普通订餐后统一回报，并在菜单未开放或只有释放库存时把请求持续推进到正常业务结果。取消、释放和换餐仍需操作前确认。本版本只对 Lincoln Square North 开放交易操作。

## 需要什么

必须具备：

- 通过分享链接或团队 GitHub marketplace 安装并启用本插件；
- Browser 或 Chrome 控制插件至少一个可用；
- 对应浏览器能打开 Aplus，且用户已完成企业登录；
- 本地个人配置目录可写。

不需要 `lark-cli`、飞书连接器、外部 MCP，也不读取密码、cookie 或 local storage。Python 3 只运行随包附带的小型 JSON 辅助脚本；没有 Python 时仍可由 Codex 完成同等操作。

## 第一次使用

可以直接说：

```text
帮我初始化字节餐厅，读取历史并展示已学到的偏好。
```

首次运行会：

1. 保留你原本的订餐诉求；
2. 检查浏览器控制、Aplus 登录、楼宇和时区；
3. 探索页面结构并建立本地操作指南；
4. 尽量读取最近 60–90 天的全部订单状态，区分明确偏好、已完成餐食证据和楼层/时间习惯；
5. 历史不足时询问一个可跳过的紧凑问题，然后继续保守订餐；
6. 展示一份简短的偏好回执、置信度和可直接使用的示例。

历史为空或页面暂时只能读取一部分，也是正常可用状态：插件不会编造偏好，也不会因为初始化不完整而中断订餐。

## 日常使用

例如：

```text
按我的偏好安排下一个可订周，完成后告诉我结果。
```

```text
把周二午餐换成猪肉锅贴，其他订单保持不动。
```

```text
监控周四晚餐的释放库存；有更好候选时先给我精确换餐清单。
```

代理会自主处理常规选菜和新订单提交，不要求逐道审核，也不会在午餐和晚餐批次之间停下来询问。全部安全批次尝试并核验后，会统一回报具体日期、餐品、楼层、时间和异常。

如果你更换了推荐餐食，插件不会直接把原菜记为“不喜欢”。它会在业务操作安全结束后最多追问一次；只有你的明确回答会更新长期偏好。

你也可以直接说：

```text
查看我的订餐偏好。
```

```text
忘记某道菜，或者重置我的全部订餐偏好。
```

## 不同时间下会发生什么

- 下周菜单尚未开放：保存请求，在预计开放后自动续跑；没有自动唤醒能力时给出准确恢复时间和一句继续指令。
- 本周已经订完：核验已有订单，不重复加购或取消。
- 部分餐段已有订单：只处理缺失餐段。
- D-2 常规订餐截止：不把它误判为绝对关闭；缺餐时继续寻找别人释放的库存。
- 距离取餐很远：低频检查，默认可到 4–8 小时一次。
- 临近取餐：逐步加快，最后两小时默认 15 分钟一次。
- 页面或登录异常：保存请求，只要求一个明确恢复动作。

## 换餐保护

Aplus 无法原子换餐，取消旧餐到提交新餐之间存在几十秒空窗。插件不会承诺消除这个风险，而是做轻量、可验证的保护：

1. 候选出现时，先展示旧餐、新餐、改善理由、空窗风险和恢复顺序；
2. 用户对这一次精确换餐确认一次；
3. 取消前立即验证候选仍可订、旧订单精确匹配、页面稳定、取消按钮属于唯一匹配订单；
4. 任一事实变化就中止并保留原订单；
5. 预检通过后不再二次确认，只取消一次并立即提交已确认候选；
6. 失败后只使用清单里已经披露的恢复路径，不静默替换成其他餐。

## 业务结果

一次调用会落在可理解、可恢复的状态，例如：

- 已全部订完并在“我的订单”核验；
- 已保留已有订单，只补缺失餐段；
- 普通订餐已连续提交并核验，结果已统一回报；
- 菜单未开放，请求已保存并安排续跑；
- 常规窗口已关闭，缺餐已进入释放库存监控；
- 保底餐已保住，正在自适应寻找明显更优候选；
- 页面或登录缺一项能力，请求已保存并给出一个恢复动作。

## 本地数据

默认保存在：

```text
~/.codex/order-bytedance-canteen/
  profile.json
  site-guide.md
  runs/
  monitors/
  pending-intent.json
```

个人偏好和订单记录不打包进插件，也不保存认证材料。

## 出现问题

可以说“生成字节餐厅脱敏诊断报告”。报告只包含插件版本、依赖状态、执行阶段和稳定错误码，不包含订单、餐食偏好、Cookie、登录信息或本地路径，也不会自动上传。
